# 0.2.2 本地场次分析与升级

Rust `archive::quality` 提供场次登记、分页快照、规则设置、判定与可取消重算。Python `QualityWorker` 仅负责唤醒一个后台分析线程；原始消息接收、入库不等待分析完成。每批提交游标、分类、人数计数，重启从已提交游标继续。读取使用 WAL 快照，导出通过临时文件原子替换。

Schema 从 v1/v2 事务迁移为 v3，保留 anchors、sessions、messages、自增序号、旧索引、外键、时长记录。v1 仍先执行活动类型迁移；v2 添加派生表。`quality_registry` 独立登记已确认的真实主播和真实场次，零消息也保留；旧 sessions/时长记录导入为覆盖未知。新记录仅承诺部分监控，不推测完整覆盖。

`quality_results` 保存每条聊天的规则版本代际、规范文本与原因；`quality_users` 累积同账号总数/有效数；`quality_groups/senders` 支持整场与窗口重复；`quality_stats` 汇总消息；`quality_commands/manual/pending` 保存已确认口令、证据与待分批处理活动；`quality_jobs` 持久化重算状态；`quality_gc` 使用索引分批回收旧代际。规则修改、口令确认和删除提升代际，旧结果立即不可见，避免被迟到工作重新写回。删除与分析共享变更门禁，原文不因分析被修改。

默认同账号 60 秒内相同内容至少 3 条、60 秒内相同内容至少 20 条且 10 人、整场相同内容至少 50 条且 20 人，回溯排除对应分组。唯一账号按 ID，同名不合并，未知 ID 单独显示消息数量。至少一条正常互动仍计有效账号。比较仅 NFC、全角 ASCII、大小写与空白，保留标点、数字、否定及表情。活动只识别明确引用的评论指令，缺少可靠时间保留待判定。无 AI，不作语义相关性推测。

扫描单批最多 128 条、可取消，原始增量与重算分配时间预算，迟到活动每批回溯最多 128 条；旧代际每表每次至多删除 64 条。单条复杂 SQL、磁盘竞争仍可能超过预算，因此预算不是硬实时保证。用户列表/样本分页，整月分析导出不通过 UI 批量传输聊天。

本机离线饱和模拟采用 300 个生产线程、300 场、30,000 条含重复内容；结果见 `build/quality-load-0.2.2.json`。该检查覆盖本地归档和并行分析，不包含抖音请求、WSS、代理或全天运行，不能证明真实 300 路平台连接。

更新恢复使用原子写入的 `update-resume.json`，只保存原/目标版本、活动任务入口 ID 和一次性 nonce，不保存凭据。确认下载并验签后写入，暂停、落盘、关闭引擎；目标版本或原版本启动时，只恢复仍存在配置中的这些任务，提交启动后删除匹配 nonce 文件。安装失败调用恢复或下次启动恢复；未知版本/无效文件保留并提示手动恢复。同场次时长沿用已有检查点，不计更新停机。正常启动没有此文件时不会自动启动任务。

**降级边界：v3 库要求 0.2.2 或更新应用。** 升级前关闭程序并备份完整数据目录；降级使用旧备份，不手工修改 `user_version`。热更新签名和 NSIS 保持原渠道与数据目录。旧版本没有新恢复逻辑，0.2.1 发起升级时仍需遵循旧流程。
