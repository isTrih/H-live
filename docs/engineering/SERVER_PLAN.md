# H-live Server：Rust + Salvo 服务端方案

状态：可行性与实施方案，尚未实现或部署服务端。默认部署方向为 Linux + Docker，等待实际服务器环境确定；继续保留现有 Tauri 桌面版。服务端不引入 Python、不使用抖音登录 Cookie、不新增礼物记录。

## 目标与复用

服务进程负责持续采集和归档，网页仅用于控制与查看；关闭浏览器、退出桌面客户端不停止服务器任务。异常退出后由进程管理器重新拉起，再恢复持久化的目标任务。不能补采断线或停机期间没有收到的消息。

新增独立 `crates/h-live-server`，通过 Salvo 提供经过鉴权的 HTTP 接口与实时事件。复用 `h-live-runtime` 的游客 HTTPS/WSS、签名、出口生命周期和采集调度，以及 `qingkan-core` 的协议、SQLite、质量规则和 CSV/XLSX。现有 UI 可增加远程数据适配器，移除网页版的原生窗口、文件对话框和桌面热更新操作，无需重做看板。

```text
浏览器 / 可选远程桌面客户端
             │ HTTPS：控制、查询、实时事件、导出下载
       Salvo 管理接口与鉴权
             │ 有界命令队列 / 阻塞调用桥接
       h-live-runtime
             │ 受出口限速和冷却控制的独立 WSS
       直播间消息 + qingkan-core 归档、分析、导出
             │
       持久化数据卷 + 独立密钥 + 定期备份
```

## 必须补齐的实现

1. **服务生命周期。** 目前 Runtime 自建 Tokio runtime，多处同步方法使用 `block_on`；Salvo handler 不能直接在异步执行上下文调用它们。首版使用有界 `spawn_blocking` 调用桥接与单一控制模块，明确退出和所有权；后续可抽出共享异步接口。SIGTERM 先进入停止接收控制请求的状态，结束事件流，取消采集并等待归档、导出和日志收尾后退出。
2. **任务恢复。** 目标运行状态先持久化再确认控制操作。开机、服务重启、故障重启后仅恢复用户要求持续监控且仍存在的任务；已停止或删除的任务不复活。沿用真实主播/场次和累计监控时间，中断间隔不计入，断线消息不伪造。
3. **Linux 凭据。** 当前配置加密使用 Windows DPAPI，非 Windows 平台会拒绝保存代理列表/订阅。需要独立凭据保护模块，使用经过审阅的认证加密库和外部注入的主密钥；不能回退到明文，也不能将 Windows DPAPI 密文直接复制到 Linux 解密。Windows 桌面旧配置兼容保留，跨机器迁移通过受控导入重新保护。
4. **远程访问。** 首版单管理员，身份验证、HTTPS 接入、写操作防护、请求大小/并发限制、操作审计和凭据脱敏。后台登录与抖音账号无关。所有数据和导出接口也必须鉴权；不把现有桌面通用 RPC 原样暴露成公网接口。
5. **远程文件。** 服务端生成随机导出任务 ID，只允许在专用导出目录生成文件，凭任务 ID 下载；不接受客户端指定服务器任意文件路径。下载和清理需遵守任务状态、授权及文件保留时间。
6. **持久化。** 首版单实例继续使用本地 SQLite 和现有 schema，数据、任务目标状态和导出文件放入持久化卷；运行日志轮转，备份采用一致快照。配置备份不能代替数据库备份。多副本不同时写同一个 SQLite 文件；多节点/多租户需要后续独立设计。
7. **运行可观察性。** 健康检查、归档队列、每出口负载/冷却、最近成功收消息时间、重试、磁盘容量与日志；补齐 Linux 进程内存/CPU 指标。现有非 Windows counters 返回缺失值，不能当作零资源使用。

## 远程接口范围

按领域暴露主播导入与管理、任务启动/停止与状态、消息查询与实时事件、场次分析、代理/订阅管理、归档删除预览与确认、导出创建/取消/下载等接口。监听地址默认仅本机或受限容器网络，对外接入显式配置。

实时流沿用有界缓存，不让慢客户端拖住采集与归档。服务实例重启后使用新的实例标识，客户端重建快照和游标；短暂断开后的显示补齐从已归档消息查询，不能将界面事件流视作唯一数据源。

## 部署与验收

- 发行包含独立 Rust 服务二进制、Dockerfile/Compose、配置模板和运维说明，不安装桌面环境或 Tauri/WebView。
- 使用非 root 进程、持久化数据卷、外部密钥及重启策略；单机部署不等于多机高可用。
- 先验证 Linux 编译和隔离端到端测试：代理加密、鉴权、任务恢复、跨月导出、删除门禁、停止写入、进程异常重启、数据卷及备份恢复。
- 再运行 300 配置任务、50 模拟并发及集中重连，增加长时间资源、队列和磁盘增长观察。Windows 28 秒离线压测不能替代 Linux 的 24 小时验收。
- 最后在实际服务器出口上做少量真实直播间观察，再渐增到目标 50 个同时开播，检查平台 444/429、退避与代理可用性，取得真实聊天和活动事件样本。

“24 小时运行”是服务持续运行和恢复的目标，不等于每个直播间永远连通或消息绝不丢失。服务器和出口变化不会消除平台限制；目前没有完成真实 50 房间或 24 小时服务端验收。
