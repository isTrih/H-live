# 0.2.2 规划：主播场次与有效发言统计

日期：2026-10-16。状态：用户已批准，0.2.2 已实现；最终打包与验证证据见 build/releases/0.2.2/release-package-report.json。

## 目标与建议

点击主播卡片，在现有居中详情弹窗中查看已监控场次数及每场的有效发言人数，能够展开查看统计依据。

建议 0.2.2 先实现本地规则统计。大量重复内容是强制无效规则，不能交由 AI 推翻。AI 适合后续辅助判断含义模糊的讨论，采用可选、按需的离线分析流程；本版核心功能不依赖 AI，也不默认附带大模型或逐条调用云端模型。

用户已于 2026-10-16 确认采用正常互动口径：相关提问、回答、评论、感谢与反馈均可；不因句子短、消极观点或没有特定关键词直接判无效。大量重复及已确认的活动参与口令仍按排除规则判无效，正常互动口径不能覆盖这些硬规则。只有字符差异很小的已证实重复可走硬规则，语义接近本身不证明重复或无效。重复检测的具体数量和时间阈值仍为待样本验证的候选参数。

## 现有代码依据

- `src/main.js` 的 `showDetail` / `updateDetail` 已提供主播详情模态框，可在该入口加入统计。
- `crates/qingkan-core/src/archive.rs` 已按真实 `anchor_id + session_id` 保存消息，包含发送人 ID、名字、内容和时间。人数可以按 ID 去重，不依赖昵称。
- 同文件 `list_sessions` 当前从 `messages` 聚合场次，零消息场次不会返回。因此不能直接把现有列表总数称为全部已监控场次数。
- `session_monitor_durations` 已保存独立场次累计监控时长，消息内容删除不会清除计时。0.2.2 应为成功确认的场次增加独立登记与覆盖记录，而不是只在第一条消息到达后登记。
- 当前按服务端 `message_id` 去重解决的是同一个事件被重传；用户真的发送多次相同内容仍是多条消息，需要单独判断重复刷屏。

## 界面与统计范围

继续使用居中模态框与现有轻圆角。顶部为主播名称、状态；下一行显示“已监控 X 场”及当前场核心统计。下方为独立滚动的场次列表，当前场在前，其余按最近观察时间倒序。

每行仅展示：直播日期、监控时长、发言人数、有效发言人数、有效发言率。点击场次后才展开重复刷屏、活动口令、其他排除及待判定数量和代表性消息，避免把全部诊断信息铺在列表中。

- 场次数：本机已确认并登记的不同真实场次，包含明确确认过但没有收到聊天或其他消息的场次，不代表主播在平台上的全部历史。
- 分页列表与总数使用同一日期筛选。默认全部已保存历史，可切换月份；跨月场次不拆成两场。
- 中途加入、断线或覆盖未知时明确标记“部分监控”或“覆盖未知”，不能称为全场分析。
- 当前场标记“统计中”；已分析数据展示分析进度，不能把尚未分析误显示为 0。
- 无法取得真实主播 / 场次 ID 时显示“场次待确认”，不创建猜测的场次。

## 核心指标

只把 `chat` 纳入发言统计；礼物、点赞、进入、关注分享、粉丝团、表情事件、活动通知另作互动信息，不加入文本发言分母。文本聊天中包含有意义的表情不因此直接排除。

| 指标 | 定义 |
| --- | --- |
| 聊天消息数 | 范围内已归档的聊天消息数量，先排除相同服务端事件重传 |
| 发言人数 | 聊天消息中具有有效发送人 ID 的不同账号数 |
| 有效消息数 | 判定为有效的聊天消息数量 |
| 有效发言人数 | 至少有一条有效消息的不同发送人 ID 数量 |
| 有效发言率 | 有效发言人数 / 发言人数；分母为 0 时显示“—” |
| 有效消息率 | 有效消息数 / 已完成判定的聊天消息数；未完成时明确为阶段结果 |
| 待判定数 | 未分析完成或无法可靠分类的聊天消息数 |
| 身份未知消息数 | 发送人 ID 缺失的聊天消息数，不以昵称代替身份计人数 |

同一个人发 20 条重复口令，再发 1 条有效提问：有效发言人数计 1，重复口令仍全部无效。没有任何有效发言的账号不计入有效发言人数。账号去重仅对当前主播场次执行，不将一个用户在多个场次的正常发言当作重复刷屏。

## 大量重复必须无效

以下参数是可调的首版候选值，需要用经过人工标注的实际直播样本验证，不是已测出的最佳阈值。

1. **单账号刷屏**：同场、同账号、60 秒内相同规范化文本达到 3 条，该窗口内该组全部判无效。
2. **多人集中刷同一句**：同场 60 秒内相同规范化文本达到 20 条，且来自至少 10 个不同账号，该组在此窗口内全部判无效。
3. **整场反复出现的固定口令**：整场同一规范化文本累计达到 50 条且至少 20 个账号，触发整场同文本组无效；与短窗口规则并存，覆盖分散刷口令。
4. **已知活动口令**：若协议明确给出参与条件文本，或用户配置了口令，且聊天精确匹配该口令，则标为活动口令。仅在消息中讨论“福袋”“红包”不能据此判无效；未收到活动通知也不能推断没有活动。
5. **机械变化**：规范化处理等价 Unicode 形式、空白和经过验证的无意义外观差异；保存原文。不得粗暴删除数字、否定词、标点或所有重复字，避免把“能退”与“不能退”、“100”与“1000”合并。

达到重复阈值后必须回溯修正该组先前的暂定结果，不能把第一条永远保留为有效。统计保存每个账号的有效消息数量；组内消息改判后，只有该账号不再有其他有效消息时，才减少有效发言人数。

规则只把命中的内容判无效，不把整个账号永久判无效。达到全场阈值后，同场后续同文本消息也按该规则处理；调整规则版本后可以重新分析。

低频短句如“谢谢”“明白了”在推荐互动口径下可以有效，集中大量刷同一句则按明确规则无效。该口径衡量去刷屏后的互动，不能直接等同于主播内容质量或推断真人率。

## AI 的边界

建议当前版本不把 AI 作为有效人数的必需依赖。没有音视频或主播逐字稿时，模型无法可靠知道“这个多少钱”“确实如此”具体回应了什么；仅凭观众消息作内容相关性判断，应允许待判定。

语义向量可以帮助寻找换说法的近似句，但其相似度不等于有效性。同主题的不同观点、相反观点和重复口令不能用同一个相似度阈值粗分。

后续若加入可选“AI 复核”：

- 仅对规则未确定的内容、去重后的代表性片段按需分析，不给 200–300 个任务逐条调用模型。
- 已命中硬重复规则的内容保持无效；AI 不能改判为有效。
- 单独保存判断、原因、模型与提示版本、置信度；低置信度或模型不可用保持待判定。
- 本地模型按需下载或连接用户已有的本地服务，云端分析需由用户主动配置并选择使用，不自动发送聊天内容。
- 先以人工标注样本比较规则与 AI 的错误类型、准确性、吞吐、内存和调用成本，再决定具体模型；本规划不推荐未经本项目中文直播样本验证的型号。
- 保留纯规则统计结果，避免用户开启不同模型后把不同统计口径的场次直接混作同一排名。

## 实现安排与性能

Rust 负责增量归一化、重复计数及场次聚合；原始消息正常归档后再异步分析，采集、ACK 和心跳不等待分析。

分析结果独立保存，包含规则版本、原因、重复组、分析进度和每账号有效消息计数。读取详情直接读预聚合结果并分页，不在每次打开弹窗时扫描整个月消息。规则变更与历史重算放入可取消后台任务。

使用限额明确的共享工作池，不按主播数量创建模型实例。短窗口计数及时过期，整场频率、回溯所需消息与分类结果使用有索引的持久化数据；设置内存和队列上限。分析落后时显示待分析数量，不丢弃原始消息，也不将溢出批次默认为有效。

对协议明确的活动条件按场次保存；先收到聊天、后到活动通知时，仅对能确定匹配范围的消息重新分析，时间或条件不明确则保留待判定，不猜活动覆盖范围。

删除记录与分析重算必须遵守同一操作门禁和数据代次。删除后旧分析任务不能重新写回已删除消息的派生结果；同范围的聚合计数必须同步更新。清理聊天后，独立已监控场次记录和计时可以保留，但该场消息分析应显示“记录已清理”而不是误称原本没有发言。旧版本缺乏登记/删除历史的数据标记未知，不倒推完整覆盖。

## 0.2.2 交付范围与验收

本版主范围：主播详情场次列表、零消息场次登记、纯规则有效发言统计、原因查看、历史后台重算，以及独立的场次分析 CSV/XLSX 导出。现有七列原始消息导出保持其既有含义；分析汇总单独提供，不把有效人数混入原始消息列。

验收至少覆盖：

- 同场暂停恢复与跨月只计一场；新场单独统计；零消息场次可见。
- 相同账号变昵称仍只计一个；不同账号同名分别计数；缺失 ID 不补造人数。
- 同服务端事件重传不增加消息/刷屏计数；真实重复发送触发规则。
- 达到阈值时回溯之前消息，纯刷屏用户退出有效人数，有其他有效发言的人仍保留。
- “有用的短回答”不因字数短直接被删；否定词和不同数值不被错误归并。
- 活动通知迟到、规则版本更新、删除与重算交错、重启恢复，不产生旧结果回写。
- 在 200–300 个模拟任务、单场极端刷屏及长历史数据下测量采集延迟、分析积压、内存和详情打开耗时；模拟结果与真实网络验证分别报告，不预先承诺吞吐数。
- AI 未配置或不可用时，核心统计与监控仍正常工作。
