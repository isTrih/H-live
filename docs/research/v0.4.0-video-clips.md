# 0.4.0 功能调研：从直播回看到视频切片

调研日期：2026-10-23。状态：方案调研，尚未实现或发布切片功能。

## 建议先做什么

建议把 0.4.0 的主线定为：**在现有回放时间轴选中一段，下载为可独立播放的 MP4，同时保留这段对应的互动证据。** 优先把当前录播获取、播放和时间对齐做稳定，再沿用这一条数据链路做导出。

| 优先级 | 功能 | 建议范围与用户价值 |
| --- | --- | --- |
| P0 | 录播可用性与分阶段错误 | 区分社区权限、解析、清单、分片网络和解码失败；明确重试状态，避免一直显示“正在加载” |
| P0 | 框选起止时间，原画切片下载 | 时间轴双端点、当前画面设为起点/终点、输入时间；展示时长、保存位置与导出方式 |
| P0 | 从亮点、红包、福袋创建切片 | 选择已有活动区间或 AI 亮点，默认前后各留余量，再由用户调整；不新增一次 AI 请求 |
| P0 | 后台任务与本地切片记录 | 下载/封装进度、取消、失败重试、打开文件夹；切片时监控继续运行 |
| P1 | 导出同步弹幕与证据 | 同名 ASS、结构化消息 JSON 和活动区间；可独立复核，不要求把弹幕压进画面 |
| P1 | 多个区间批量下载 | 选中几个亮点后逐个排队；复用已下载分片，避免重复取整场 |
| P2 | 精准裁剪、兼容转码、烧录弹幕 | 需要编码链路、性能和分发决策，放在快速切片稳定之后 |
| 暂缓 | 正在直播时自动录制、自动剪辑合集 | 当前依赖上游已同步录播 URL，不能据此承诺实时录屏、未同步内容或历史缺失内容可下载 |

这些优先级与后文的并发数、时限、工期都是针对本项目的设计建议，区别于上游已实现能力。

## 快速无损切片和精准裁剪要分开

FFmpeg 的 stream copy 直接搬运压缩数据，不解码和编码，速度快且不引入重编码画质损失，但不能应用视频滤镜。输入端 `-ss` 通常定位到目标之前的可寻址点；重编码时默认 accurate seek 可以解码并丢弃前面的内容，stream copy 则可能保留。因此 **`-ss ... -c copy` 不能宣传成任意位置逐帧精确裁剪**。其进度可以由 `-progress pipe:1` 的结构化键值读取。[FFmpeg 命令文档](https://www.ffmpeg.org/ffmpeg.html)

建议第一版的产品名称为“原画快速切片”：

1. 用户选定希望得到的 `[start_ms, end_ms)`。
2. 下载计划覆盖所需分片与解码起点；探测关键帧后，展示实际起止范围。HLS 分片边界不一定就是独立可解码的关键帧边界。
3. 原画模式从可独立解码的起点开始封装，记录 `requested_range` 和 `actual_range`。若找不到可验证的起点，明确失败，不产出开头黑屏的“成功文件”。
4. 精准模式以后使用“解码 → 丢弃范围外帧 → 重编码”；音频也要重新建立相对时间。只重编码首尾再拼接中段属于额外工程，不是本期捷径。

命令形状仅作说明，尚未在本项目验证。正式实现传参数数组，不拼接 shell 命令；输入是 Rust 下载器生成的本地清单，`COPY_START` 已由计划确认：

```text
ffmpeg -nostdin -hide_banner -loglevel error -progress pipe:1
  -ss COPY_START -i LOCAL_MANIFEST -t ACTUAL_DURATION
  -map 0:v:0 -map 0:a:0? -c copy -movflags +faststart
  -f mp4 OUTPUT.mp4.part
```

输出完成后用 ffprobe 校验，再原子改名。`faststart` 把 MP4 索引移至文件前部，便于下载后快速打开，但需要收尾处理，所以进度不能在下载结束时直接显示 100%。未封装完成的普通 MP4 不应以正式文件名暴露。[FFmpeg MP4 封装说明](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/muxers.texi)

## HLS 不能简单截几条 URL 再拼起来

HLS 的 PDT 将某个分片的首个媒体样本与绝对时间关联；discontinuity 可能表示时间戳序列、轨道或格式发生变化。相关标签还包括独立音轨、初始化段、字节范围、加密状态、媒体序号。跨中断不能一律用“首个 PDT 加累计时长”推算墙钟时间；也不能用不同 rendition 的相同 media sequence 直接配对。[RFC 8216，§4.3.2、§4.3.3、§4.3.4、§6.2.1](https://www.rfc-editor.org/rfc/rfc8216)

建议新增只描述计划的结构，媒体时间和真实时间都保留：

```text
ClipRequest:
  session_id, video_id?, start_media_ms, end_media_ms,
  mode, destination, time_correction_ms

ClipPlan:
  source_fingerprint, requested_range, actual_range,
  chosen_variant, chosen_audio,
  segments[{rendition, sequence, discontinuity_sequence,
            media_start_ms, duration_ms, wall_start_ms?,
            byte_range?, init_id?, local_file}],
  mapping_quality
```

具体规则：

- 用户手动框选以**播放器媒体时间**为准，PDT 不完整也能切片；从红包、福袋或聊天创建切片时，先通过现有映射转为媒体时间。
- 映射落在未知区间、墙钟空洞或出现多个候选时，不静默跳到最近片段；提示重新校准或由用户在画面上选定。单个偏移不能修复多处中断造成的不同偏移。
- 按区间收集视频和音频；若 master 使用独立音频，不能只截取 video variant。下载时固定 rendition，避免中途自适应切换改变参数。
- `EXT-X-MAP`、`BYTERANGE` 和中断标签必须保留相应语义。跨中断还要比较编码参数；不兼容时分文件输出或进入重编码流程。
- 首版限于已结束、无加密的 HLS VOD，以及可定位的 MP4。AES-128、SAMPLE-AES、DRM 和仍在滑动的 live 清单暂不纳入承诺。以后支持 AES-128 时，截取后还要正确保留原 media sequence/IV，不能简单从 0 重编号。
- 不能把 TS 文件按字节拼接后改名 MP4；需要 demux/remux。FFmpeg 的 concat demuxer也要求各输入流结构、编码和 time base 兼容，不能把它当作跨任意 discontinuity 的万能修复。[FFmpeg demuxer 源文档](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/demuxers.texi)

## 推荐技术路径

建议保留现有播放器，在 Rust 中实现独立 `ClipService`，由 FFmpeg/ffprobe 作为受控导出工具。先写通本地清单切片原型，再接 UI；不为下载功能替换整个播放引擎。

```text
时间轴选区 / 活动区间 / 亮点
  → ClipRequest 校验
  → 复用原生 resolver 获取新 URL
  → 解析完整 HLS 结构 / 有界 ffprobe
  → ClipPlan（固定画质、音轨、实际范围）
  → Rust 仅下载所需分片及必要前置分片
  → 本地清单 → FFmpeg 封装
  → ffprobe 校验 → 原子改名 → 切片记录
```

这样网络请求继续使用本应用的凭据隔离、直连/代理策略和可取消下载；FFmpeg 主要处理本地文件，避免把社区 KEY、带签名地址、任意远程清单直接交给子进程。ffprobe 能输出 JSON 的容器与流信息，并提供按区间探测选项；远程探测仍可能读取额外数据，必须由父进程设置超时和下载预算。[ffprobe 源文档](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/ffprobe.texi)

建议模块边界：

| 模块 | 职责 |
| --- | --- |
| `clip_plan` | 纯数据：区间、时间转换、分片/音轨选择、边界与兼容性判断；脱敏 fixture 可测 |
| `clip_download` | 域名/跳转限制、有界下载、缓存、取消、URL 刷新 |
| `clip_worker` | 固定工具路径、参数数组、进度解析、超时、进程回收和输出验证 |
| `clip_jobs` | 排队、任务记录、状态机、更新/退出协调；不持有监控状态锁执行 IO |
| `clip-ui` | 双端点选区、实际范围、进度、错误与本地记录 |

不建议首版把任意 `ffmpeg` 命令或本地可执行路径开放给前端。桌面版可由 Rust 内部进程 API 启动固定工具；若采用 Tauri sidecar，官方要求按目标 triple 分别准备二进制并配置 `externalBin`，同样应收窄调用能力。[Tauri 外部二进制](https://v2.tauri.app/develop/sidecar/)

## Windows 编码与 alhazen 的边界

**MP4 是容器，不能保证所有电脑都能播放。** 同为 MP4，H.264/AAC 与 HEVC/AAC 的系统兼容性不同。Microsoft 的 Edge 排障资料把 HEVC 列为有条件支持，需要有效的 HEVC 扩展和可用解码路径；不能将开发机成功播放外推为所有 WebView2 电脑可播放。建议用 Windows 10/11、不同 GPU、无额外 HEVC 扩展机器做实际验收。[Microsoft Edge 播放与编码支持](https://learn.microsoft.com/en-us/troubleshoot/microsoft-edge/development/video-playback-issues)

建议：首版默认验收 H.264 + AAC → MP4。遇到 HEVC 时，可明确提示“保留原编码，部分播放器可能不支持”，或暂不提供导出；重封装不会把 HEVC 变成 H.264。后续“兼容 MP4”才进行 H.264/AAC 转码。Windows 可研究 FFmpeg `h264_mf`/Media Foundation，macOS 可研究平台编码器，但实际可用性、画质与失败降级仍需原型。FFmpeg 提供原生 AAC 编码器，不应默认引入额外 AAC 库。[FFmpeg 编码器文档](https://ffmpeg.org/ffmpeg-codecs.html)

alhazen-core 的上游定位是原生播放器/解码引擎：读取文件或 URL，提供画面帧和音频；支持 HLS、平台解码与部分纯 Rust 解码。此次没有在公开 README/接口定位中找到可承诺的“区间导出 MP4 + 视频编码”工作流，所以不能把“可播放 HLS”理解为“可精准裁剪和封装”。它还不直接把帧绘制进 HTML video，切换会影响现有弹幕与全屏组合。[alhazen-core 官方仓库](https://github.com/alhazen-rs/alhazen-core)

其当前仓库 manifest 为 0.6.0、Rust 1.92、Apache-2.0；默认功能并非全部纯 Rust，包含平台 API 以及可查找用户 FFmpeg 的回退路径。纯 Rust 解码能力也不等于提供 H.264/HEVC 纯 Rust 编码器。是否将它用于其他原生播放场景可另作小原型，不建议成为 0.4.0 切片的依赖前提。[上游 Cargo.toml](https://raw.githubusercontent.com/alhazen-rs/alhazen-core/master/Cargo.toml)

### 补充：星图是否提供 H.264 备用码流

2026-10-23 补查了用户既有 HAR 中的第一方脚本，并重新匿名读取公开样本 API 和同版播放器脚本；未请求社区 KEY、未下载媒体。`CommonPlayer-DLnGulcK.js` 只按 `video_id` 查询并消费单个 `play_url`，没有 H.264/AVC 选择或回退。样本 API 仍返回 `base_resp`、`cover`、`duration`、`height`、`play_url`、`width`，未见备用 URL/码流数组或 codec 字段。HAR entry 52 的 API wrapper 参数列表也未见 codec 选择。依据：[第一方播放器脚本](https://lf-star-static.bytetos.com/obj/star-scm-static/star/idou_fe/assets/CommonPlayer-DLnGulcK.js)、[第一方 API wrapper](https://lf-star-static.bytetos.com/obj/star-scm-static/star/idou_fe/assets/go_generic-sxaiKznH.js)、[公开样本 API](https://www.xingtu.cn/gw/api/ggeneric/get_video_info?video_id=v0220dg10001db0csri7dld189kvt2g0)。

结论限于这些可见证据：**没有找到可承诺的 H.264 备用地址或切码流参数**，不证明平台内部完全不存在；不应猜 `codec_type` 等参数上线。对只提供 HEVC 的源，仅改容器或用 HLS.js 不能消除系统解码限制。要避免要求用户安装 HEVC 扩展，需要另行验证自带解码/转码路径；当前 WebView 方案无法据此承诺所有 Windows 电脑直接播放。

## 工具分发、许可与体积

FFmpeg 的默认许可是 LGPL 2.1 或后续版本；启用 GPL 组件会改变 FFmpeg 构建本身的许可，`--enable-nonfree` 组合可能产生不可再分发的构建。不要拿一份“完整版”二进制就认定满足发布要求。建议先采用明确构建参数、精确源码、校验值和许可证材料的 LGPL 工具包，避免 `--enable-gpl`、`--enable-nonfree`、libx264/libx265/libfdk-aac 等未经确认的组合。外部进程隔离不取消对实际分发的 FFmpeg 本身的履约要求。[FFmpeg 许可页](https://www.ffmpeg.org/legal.html)、[FFmpeg LICENSE](https://ffmpeg.org/doxygen/trunk/md_LICENSE.html)

对 H-live 的发布建议：

- 优先“首次导出安装媒体工具组件”，用户客户端只从现有公司内网站点下载固定版本，验证签名清单、SHA-256、架构和工具版本；缓存到版本独立目录。
- 官网下载区、应用关于页同时提供 FFmpeg 归属、准确源码/构建参数和许可证材料；具体合规做法应按最终构建与调用方式确认，不能只在文档写一句“LGPL”。
- 基础客户端继续保持小包；也可以提供包含媒体组件的完整安装包。工具升级和应用升级分开，工具包失效不阻止基本监控。
- 不把不固定的 `latest` 构建直接作为正式依赖，不在用户电脑任意搜索并执行不可信 PATH 中的同名程序。

体积证据：本次只查询构建维护者自己的 GitHub Release 元数据，未下载工具。查询时 `ffmpeg-master-latest-win64-lgpl-shared.zip` 为 **82,096,106 字节（约 78.3 MiB）**，静态完整 ZIP 为 **177,958,144 字节（约 169.7 MiB）**。这是第三方构建维护者发布的**整个工具包**，不是 FFmpeg 官方二进制，也不是 H-live 最终裁剪组件体积；不能直接把这些数字计为安装包增量。[BtbN 发布资产元数据](https://api.github.com/repos/BtbN/FFmpeg-Builds/releases/latest)

作为对照，本地现有 0.3.8 安装包为 10,053,281 字节（约 9.6 MiB）。最小构建能小多少、DLL 共用后的 ffmpeg/ffprobe 合计大小、压缩后和磁盘占用，均需实际构建测量。本次没有构建；不建议对用户承诺“只增加几 MB”。

## 时效 URL、进度、取消与重试

签名 URL 的具体寿命未得到星图稳定公开契约，应继续保存场次 ID、video_id 和原始页面标识，任务开始时重新解析，不推算或删改签名参数。

建议任务状态：

```text
queued → resolving → planning → downloading → muxing → validating → completed
                                               ↘ failed / cancelled
```

- 解析、下载、封装分别展示状态。下载进度按完成字节/分片计算；未知总量显示不确定进度，不能用经过时长伪造 90%。FFmpeg 阶段使用输出媒体时间计算进度，验证通过前保留收尾状态。
- 默认同时执行 1 个切片任务、2 个分片连接，上限先限定为 4 个；相同源短时间内共用只读分片缓存。上述是初始资源策略，待性能数据再调整。
- 网络错误和 5xx 做有上限的指数退避；429 尊重 Retry-After。明确权限错误直接返回，不能反复重试消耗 KEY 请求。FFmpeg 本身有 reconnect、HTTP 状态与退避选项，但不能替应用完成业务 URL 重新解析。[FFmpeg 网络协议文档](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/protocols.texi)
- 分片 403/410 时至多重新解析一次并重新规划；API 本身的 401/403 归为权限错误。新清单必须核对 video_id、结构指纹、区间和编码，不能因为序号相同就接着旧任务拼接。
- 缓存续传只接受已完整写入、长度/哈希确认的分片；中断的 `.part` 删除重取。MP4 直连 Range 续传需要验证 206、Content-Range 和资源标识，不把整个下载当成可任意续接的字节流。
- 下载用取消 token；封装取消后结束子进程并回收子进程树。删除本任务临时文件，正式输出只在验证成功后出现。应用更新/退出要等待或取消视频任务，纳入现有导出保护。
- 建议 UI 响应取消不超过 2 秒；超时回收可用 5 秒硬上限。连接、首字节、单分片、重试总预算都需显式设置，具体数值通过公司网络与用户实际线路验证。

## 弹幕：先伴随文件，再考虑烧录

建议默认导出原画 MP4，可勾选同名弹幕文件：

| 方式 | 效果 | 建议 |
| --- | --- | --- |
| JSON/CSV 消息伴随文件 | 可保存发送时间、内容、活动和证据 | 易复核；只导出该切片范围，默认不包含账号 ID |
| ASS 伴随字幕 | 支持滚动位置、颜色和半透明底；需要支持 ASS 的播放器 | 先做，单独开关，不声称所有系统播放器自动加载 |
| MP4 软字幕 | 通常只保留普通文本字幕，不能承诺复现滚动与灰底布局 | 可后续提供阅读模式，别与完整弹幕效果混淆 |
| 烧录到画面 | 外部播放一致，无法关闭，需要重编码 | 后置，确认字体、编码器、性能及发布组件后再上 |

FFmpeg 的 `ass`/`subtitles` 滤镜使用 libass 把字幕画进视频，增加对应依赖和字体分发问题；当前浏览器中的 DOM/CSS 弹幕不会自动进入导出文件。[FFmpeg 字幕滤镜源文档](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/filters.texi)

对齐规则应以最终 `actual_range` 为零点。活动/消息先从墙钟转成媒体时间，再减去实际切片起点；跨中断分别映射。裁剪起点之前已经进入画面的滚动弹幕，如需保留，应读取一个显示时长的前置窗口并裁掉字幕的负时间部分。消息中的花括号、反斜杠、换行和控制字符要按 ASS 语法转义，不能把聊天当作字幕脚本指令。

## 凭据与本地数据边界

延续当前社区开关的约束：KEY 仅由原生后端保存和访问固定社区 API；不写入 HTML/JS、打包 `.env`、任务 JSON、字幕、导出元数据、FFmpeg 参数或日志。媒体站点请求不携带社区 Authorization。

Rust 下载器需要继续逐个验证清单、音轨、分片、初始化段和跳转的来源；不能仅验证首个 m3u8 后允许其读取任意内网地址或本地文件。可执行工具仅从受信组件目录启动，生成的本地清单也只引用本任务缓存目录。临时签名清单访问受限，结束后清理；任务记录存稳定来源标识与本地结果，不保存完整签名 URL。

## 0.4.0 MVP 边界与验收门槛

建议首版包含：Windows 桌面、已结束录播、无加密 TS-HLS / MP4、H.264/AAC、单个范围原画下载、关键帧边界提示、后台队列/取消/重试、切片本地记录、选中活动/亮点生成范围。ASS/消息伴随文件可作为时间允许后的增量。暂不承诺无录播场次、实时录制、任意 URL、DRM、精准到帧、自动混剪或 HEVC 转码。

以下为**待执行的验收标准**，不是此次已通过的测试：

| 领域 | 最低验收 |
| --- | --- |
| 核心输出 | 选择开头、中段、结尾，生成有声有画 MP4；无音轨输入也能明确处理；输出流、时长和首帧通过探测及实际播放验证 |
| 范围诚实 | 显示 requested/actual 起止；实际边界与计划一致；快速模式不标“逐帧精准” |
| 网络用量 | 以本地可控服务器验证只请求选中区间及必要前置/初始化/音轨，不能先下载整场再裁剪 |
| 时钟 | 覆盖 PDT 缺失、跨 discontinuity、墙钟空洞、重复墙钟、手动校准；不自动把未知映射套成连续时间 |
| HLS 结构 | master + 独立音频、相对 URL、fMP4 init/byte-range 明确支持或明确拒绝；中断后参数变化不产坏文件 |
| 可恢复 | 注入分片断网、403/410、API 401/403、429、5xx；只对允许情况有限重试，刷新后不串源 |
| 取消与磁盘 | 取消后无残留进程、不出现假成功 MP4；磁盘满、中文路径、超长/非法文件名、重复目标名均有明确结果 |

| 发布 | 全新 Windows 10/11 能安装、验证并运行媒体组件；损坏包拒绝；组件不可用时基本监控仍可运行 |
| 隐私 | 编译产物、站点包、日志、任务记录与字幕扫描不出现测试 KEY/签名 URL；不把原生密钥发给媒体域名 |

建议先做 1–2 天原型：使用项目自产、可控的短 H.264/AAC HLS fixture，验证“时间段计划 → 下载 → 无损 MP4 → 首帧/声音/范围”，再用有权限的真实录播小片段验收。没有用户授权和可用 KEY 时不宣称真实场次通过。

粗略排期（1 名熟悉本仓库的工程师，不含不可控上游问题）：原型 1–2 天，下载计划/队列与清理 2–3 天，时间轴选区/活动入口/任务 UI 1–2 天，组件发布与 Windows 验收 2–3 天，总计约 **6–10 个工作日**。精准重编码与烧录弹幕另估，不作为 0.4.0 首发硬条件。

最高风险是上游录播权限/时效、带 discontinuity 的真实音视频时间线、以及 Windows 编码路径和媒体组件发布。先让普通切片稳定得到一个能播、范围可解释的文件，再扩大格式与自动化范围。
